# 首次请求 80 秒延迟根因分析

## 前置知识：stdin / stdout / stderr

### 什么是标准流？

每个进程启动时，操作系统会提供三个默认的 **I/O 流**（文件描述符）：

| 流 | 编号 | 名称 | 默认方向 | 用途 |
|-----|------|------|---------|------|
| **stdin** | 0 | 标准输入 | 键盘 → 进程 | 进程从这里读取输入 |
| **stdout** | 1 | 标准输出 | 进程 → 屏幕 | 进程的正常输出 |
| **stderr** | 2 | 标准错误 | 进程 → 屏幕 | 进程的错误/诊断信息 |

### 在 Python 中

```python
print("hello")          # 写入 stdout（文件描述符 1）
logger.info("hello")    # 写入 stderr（文件描述符 2），因为 logging.StreamHandler 默认目标就是 stderr
sys.stderr.write("x")   # 直接写 stderr
sys.stdout.write("x")   # 直接写 stdout
```

### 为什么 logger.info 走 stderr？

`logging.StreamHandler()` 的默认输出目标是 `sys.stderr`。这样设计的好处是：
- **stdout** 放程序的主要输出（如 AI 的回复内容）
- **stderr** 放诊断/调试信息（如日志、错误栈）
- 在 shell 中可以分别重定向：`python app.py > output.txt 2> error.log`

### print 走的是 stdout

`print("xxx")` 默认写入 stdout。但如果用了 `print(..., file=sys.stderr)` 也可以写到 stderr。

### 在本项目中的实际表现

后端进程被前端（Electron/Wails）以**子进程**方式启动。前端通过**管道（pipe）**分别捕获 stdout 和 stderr：

```
后端 Python 进程
    ├── stdout ────[管道]───→ 前端显示为 [Backend]
    ├── stderr ────[管道]───→ 前端显示为 [Backend ERR]
    └── HTTP/WS ──[网络]───→ 前端处理业务数据
```

### 管道缓冲与阻塞

操作系统管道有一个**固定大小的缓冲区**（Windows 通常 4KB~64KB）：

```
后端 write("A" * 96000) → [██████████████████████████████... 管道缓冲 4KB] → 前端 read()
```

当后端写入速度远超前端读取速度时：
1. 缓冲区被填满
2. `write()` 系统调用**阻塞**，等待前端读取腾出空间
3. 前端如果还没开始读取（比如在等 HTTP 响应），就一直堵着

这就是本次 bug 的机制：96KB 数据试图写入 4KB 的 stderr 管道，而前端还没开始读，write() 阻塞 82 秒。

### stdout/stderr vs HTTP vs WebSocket

| 特性 | stdout/stderr | HTTP | WebSocket |
|------|--------------|------|-----------|
| **方向** | 后端 → 前端（单向） | 双向（请求-响应） | 双向（全双工） |
| **传输方式** | 操作系统管道 | TCP 网络 | TCP 网络 |
| **数据格式** | 纯文本流 | 结构化（JSON等） | 二进制帧 |
| **用途** | 日志、调试信息 | API 调用 | 实时推送（流式响应） |
| **缓冲区问题** | **有**（管道缓冲小） | 无（网络层处理） | 无（网络层处理） |
| **是否阻塞** | **会**（写满管道阻塞） | 不会（异步） | 不会（异步） |

**总结**：stdout/stderr 是给**开发者看**的日志通道，HTTP/WebSocket 是给**程序处理**的数据通道。绝不能用 stdout/stderr 传输业务数据（如完整消息列表），应该走 HTTP/WebSocket。

### 为什么直开前端不卡，通过启动器就卡？

本项目的两种运行方式：

| 方式 | stdout/stderr 去向 | 是否可能阻塞 |
|------|--------------------|------------|
| **直接启动**（`python main.py`） | 终端（console）— 终端持续读取管道 | ❌ 不会，终端永远在消费输出 |
| **通过 Wails 启动器** | Wails 的 Go 进程通过 pipe 捕获 → 前端显示 | ✅ **会**，如果 Wails 进程没及时 read() |

关键区别：终端由 OS 管理，始终在读取 stdout/stderr。而 Wails 启动器在自己有空时才去读取 pipe。如果 Wails 正忙着处理 HTTP 请求（等 AI 响应），它可能暂时不读取 pipe，导致管道缓冲区堵死。

## 排错过程

### 第 1 步：发现"前置准备（总计）"耗时异常

在 `_stream_ai_response()` 开头设置 `_stream_start = time.perf_counter()`，末尾打印总耗时。
发现前置准备总耗时 101,639ms ≈ **101秒**，但内部所有子步骤只有 ~1.4 秒。

### 第 2 步：给所有 `print()` 加 `flush=True`

怀疑 stdout 缓冲导致日志延迟显示。添加后：
- 耗时从 **101 秒 → 81 秒**（减少了约 20 秒 —— 这是 stdout 缓冲被刷出来的时间）
- 但 81 秒仍然异常，说明卡点不在 stdout，而在 stderr

### 第 3 步：逐段加计时，缩小范围

在每段代码周围加 `time.perf_counter()` 计时，最终定位到：

```
[耗时] 构建上下文消息: 182.2ms
[耗时] 消息列表 f-string 格式化: 1.6ms, 长度=96353  ← 96KB！
[耗时] logger.info 写入: 81956.0ms                   ← 81秒！！！
[耗时] 构建 call_kwargs: 0.0ms
```

**`logger.info()` 写入 stderr 花了 81 秒**，而 f-string 格式化只花了 1.6ms。

### 第 4 步：确认根因

`logger.info(f"环境信息：{messages_with_context}")` 将 **96KB** 的完整消息列表写入 stderr 管道。
首次请求时前端还没开始读取管道，管道缓冲区瞬间填满，`write()` 系统调用阻塞 81 秒。

### 第 5 步：修复

将 96KB 的日志改为只输出消息数量：
```python
# 改前
logger.info(f"环境信息：{messages_with_context}")  # 96KB → 阻塞 81 秒

# 改后
logger.info(f"环境信息构建完成，共 {len(messages_with_context)} 条消息")
```

**修复后首次请求耗时从 81 秒降到 2.9 秒。**

## 问题现象

每次后端启动后，**第一个对话请求** 会卡 80~100 秒才开始响应。后续请求都正常（8 秒左右完成）。

## 根因

**罪魁祸首：[`backend/api/chat_api2.py:418`](backend/api/chat_api2.py:418)**

```python
logger.info(f"环境信息：{messages_with_context}")
```

这行日志将完整的消息列表（system prompt + 历史 + 上下文环境信息）格式化为一个 **96KB** 的字符串，然后通过 `logger.info()` 写入 stderr。

### 阻塞机制

1. 后端进程将 stdout/stderr 通过管道（pipe）发送给前端进程（Electron/Wails）
2. 操作系统管道缓冲区默认只有 **4KB~64KB**（Windows 上通常为 4KB）
3. 首次请求时，**前端尚未开始从管道读取数据**（前端在等待 HTTP 响应返回后才开始处理子进程输出）
4. 当 logger.info() 试图将 **96KB** 数据写入 stderr 管道时，**管道缓冲区瞬间填满**
5. `write()` 系统调用阻塞，等待前端读取腾出空间
6. 前端直到 HTTP 响应抵达后才开始读取管道，write() 才得以继续
7. 阻塞时间 = `96KB / pipe_buffer_size * 调度延迟` ≈ 80 秒

### 为什么后续请求不卡

前端一旦开始读取管道，会持续消费数据。后续请求的 write() 调用不会被阻塞。

## 解决方案

**禁止在关键路径上向 stderr/stdout 写入大数据量。**

将 [`chat_api2.py:418`](backend/api/chat_api2.py:418) 的：

```python
logger.info(f"环境信息：{messages_with_context}")  # 96KB
```

改为：

```python
logger.info(f"环境信息构建完成，共 {len(messages_with_context)} 条消息")
```

### 预防措施

所有 `print()` 和 `logger.info()` 的输出大小应当控制在合理范围内（< 1KB）：
- 不要在性能关键路径上输出完整数据结构
- 大型数据（文件树、RAG 结果、完整消息列表）只输出长度/条数摘要
- `print()` 一定加 `flush=True`，避免 stdout 行缓冲导致的类似问题
- 如果确实需要调试大型数据，使用写文件方式，不要走管道

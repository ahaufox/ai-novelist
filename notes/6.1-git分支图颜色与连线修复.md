# 6.1 Git 分支图颜色与连线修复

## 原始问题

启动器的 Git 分支图（`GitGraphCanvas`）渲染效果很差：
- 每个 commit 之间的线条颜色各不相同，五颜六色乱成一团
- 期望：按**分支**分配颜色，每个分支一个颜色，主分支一个色、各 feature 分支各一个色

---

## 第一轮：改颜色分配逻辑

### 尝试 1 — 分支名 → 颜色

**改法**：原来用 `pickColor(r.sha)` 给每个 lane 分配颜色（SHA 哈希 → 15 色调色板），不同 commit 不同颜色。改为从 `refs` 中提取分支名（去掉 `HEAD -> ` 和 `origin/` 前缀），用分支名做哈希种子。

**结果**：全部灰色，没颜色。

### 调试日志

```
[GitGraph] 有 refs 的 commit 数: 1
[GitGraph]   lane=138 row=181 refs=[HEAD -> main, origin/main, origin/HEAD]
[GitGraph] lane 138 → 分支 "main"
[GitGraph] 最终 laneColor 映射: [[138, '#4CAF50']]
```

182 个 commit，只有 1 个有 refs（HEAD tip），且它在 lane **138**。意味着 lane 分配算法有严重 bug——线性链 A→B→C 应该全在 lane 0，却产生了 138 个 lane。

### 根因：lane 分配算法 step 3 的 bug

```typescript
// 原算法 step 3：为每个子 commit 预分配 lane
for (let j = i + 1; j < sorted.length; j++) {
  const child = sorted[j];
  if (child.parents.includes(c.sha) && !laneOf.has(child.sha)) {
    // ❌ 总是分配新 lane，阻断了父→子的 lane 继承
    laneOf.set(child.sha, lanes.length);
    lanes.push(child.sha);
  }
}
```

线性链 A→B→C 处理过程：
- A 被处理时，step 3 把 B 预分配到 lane 1（而非继承 A 的 lane 0）
- B 被处理时，step 3 又把 C 预分配到 lane 2
- 结果：A(lane 0)、B(lane 1)、C(lane 2)……每个 commit 一个 lane

### 尝试 2 — 修复 lane 分配

用 children map 替代 step 3：第一个子 commit 继承当前 lane，其余子另开新 lane。

**结果**：还是不对。手写 lane 分配难以覆盖所有 git 拓扑情况（merge、fork、多个父 commit 等）。

---

## 第二轮：改用 git 自身的 `--graph` 输出

**决策**：git 自身的 `git log --graph --all` 经过数十年验证，lane 分配绝对正确。不要自己实现，直接用 git 的输出。

Go 后端已有 `GetGraphOutput` 函数，调用 `git log --graph --all --format=...`，用 `\x1F` 作为字段分隔符。

### 尝试 3 — 直接使用 `\x1F` 分隔符

**改法**：
- `GitManager.tsx` 数据源从 `GitAllCommits` 改为 `GitGraphOutput`
- `GitGraphCanvas.tsx` 从 git graph 前缀解析 lane：`lane = starIdx / 2`

**结果**：lane 分配正确了，但跨 lane 连线全部消失（fork/merge 线不显示）。

### 调试日志

```
[Graph] MISS rowOf: child=3163b2a row=0 lane=0 parent=尝试修复前端缓
```

`parent` 字段存的是**中文 commit message**，不是 parent SHA！字段解析错位了。

### 尝试 4 — 改用 tab 分隔符

怀疑 `\x1F`（ASCII 31, Unit Separator）控制字符在 Windows 命令行 `os/exec` → `git.exe` 传递时被吃掉。

改用 `%x09`（tab），让 git format 自己输出 tab 字符：

```go
const graphFormat = "--format=%H%x09%P%x09%s%x09%an%x09%aI%x09%D"
```

**结果**：仍然不行，tab 方案也没能解决。

---

## 最终方案：两步合并

### 核心思路

不依赖于任何分隔符在 `--format` 中传递结构化数据。改为：

1. **`git log --graph --all --format=%H`** — 只输出 graph 前缀 + 40 位 hex SHA（**纯 ASCII hex，无任何分隔符问题**）
2. **`GetAllCommitDetails`** — 复用已有可靠实现（用 `|` 分隔符，已在 commit 列表功能中验证可用）
3. **Go 中按 SHA 合并** — 从 SHA 反查 commit 详情

### Go 实现

```go
func GetGraphOutput(projectDir string, maxCount int) ([]GraphLine, error) {
    // 步骤 1：graph 拓扑（只拿 SHA）
    graphOut, _ := gitutil.CombinedOutputIn(projectDir,
        "log", "--graph", "--all", "--format=%H",
        fmt.Sprintf("--max-count=%d", maxCount))

    // 步骤 2：commit 详情（已有可靠实现）
    details, _ := GetAllCommitDetails(projectDir, maxCount)
    detailMap := make(map[string]CommitDetail)
    for _, d := range details {
        detailMap[d.SHA] = d
    }

    // 步骤 3：解析 graph 输出 + 合并详情
    for _, line := range strings.Split(graphOut, "\n") {
        sha := extractTrailingSHA(line) // 提取行末 40 位 hex
        if sha != "" {
            // commit 行：graph 前缀 = 去掉末尾 SHA
            d := detailMap[sha]
            lines = append(lines, GraphLine{...})
        } else {
            // 连接线行（|\  |/  等）
            lines = append(lines, GraphLine{Graph: line, IsCommit: false})
        }
    }
}
```

### 前端 SVG 渲染重写

改为三层结构：

**第 1 层 — 连续 lane 竖线**（替代之前逐行穿越线）

```tsx
{Array.from({ length: maxLane }, (_, li) => {
  const commits = rows.filter(r => r.lane === li);
  if (commits.length < 2) return null;
  const minRow = Math.min(...commits.map(r => r.row));
  const maxRow = Math.max(...commits.map(r => r.row));
  return <line x1={x(li)} y1={y(minRow)+DOT_R} x2={x(li)} y2={y(maxRow)-DOT_R} ... />;
})}
```

每列一根竖线，从该 lane 最老 commit 连续画到最新 commit。不再断断续续。

**第 2 层 — 跨列连接线**（fork/merge）

- Fork（分叉，`pi === 0` 且不同 lane）：┐ 形 L 折线
- Merge（合并，`pi > 0`）：贝塞尔曲线
- 同 lane 连接跳过（已被连续竖线覆盖）

**第 3 层 — 圆点 + message + refs 标签**

### 颜色分配

每个 lane 必定有颜色：

```typescript
const seed = branch || `lane-${r.lane}`;
m.set(r.lane, hashToColor(seed));
```

- 有分支名的 lane（如 main）：用分支名做种子 → 同一分支始终同色
- 无分支名的 lane（已合并/删除的分支）：用 `lane-N` 做种子 → 不同 lane 不同色

## 教训

1. **Windows 命令行传递控制字符不可靠**：`\x1F`、`\x00` 等 ASCII 控制字符在 `os/exec` → `CreateProcess` 链路上会被丢弃，不能用作分隔符
2. **git 本身的 `--graph` 是唯一可靠的 lane 分配方案**：手写算法极难覆盖所有 git 拓扑场景（merge、fork、octopus merge 等）
3. **分步 + 合并比一步到位更可靠**：graph 拓扑和 commit 详情分开获取，各自用最可靠的方式解析，最后按 SHA 合并

## 第三轮（6.2）：架构重构 — Go 端解析 → 前端纯渲染

### 背景

第二轮方案将 `GraphLine[]`（含 ASCII graph 字符串）传给前端，前端逐字符解析并手算 fork/merge 线。存在以下问题：

1. **连接线数据被浪费**：`--graph` 输出的连接线行（`|`、`\`、`/`）传给前端但被 `continue` 跳过，前端又用 `parents` 数组重新手算 fork/merge
2. **手算连线不完整**：fork/merge 后回到主线的竖线缺失（git 在 `|/` 下一行输出 `*` 时不输出 `|`）
3. **分支内部竖线缺失**：`\` 引入的新 lane 没有显式 `|`，导致分支 commit 之间缺竖线
4. **前端逻辑复杂**：~270 行 TypeScript，5 个 `useMemo`，多种边界情况处理

### 新架构

**核心决策**：Go 端完成所有 `--graph` 解析 + 颜色分配，前端只画 SVG 图元。

#### Go 端新增 `GetStructuredGraph`

数据流：

1. `git log --graph --all --format=%H` → graph 拓扑骨架（SHA 无需分隔符）
2. `GetAllCommitDetails` → commit 详情（message/author/date/refs）
3. 逐行逐字符扫描 graph 前缀：
   - 偶数位 `|` → `SegData{type:"vline"}`
   - 偶数位 `*` + SHA → `NodeData{sha, message, ...}`
   - 奇数位 `\` → `SegData{type:"fork"}`
   - 奇数位 `/` → `SegData{type:"merge"}`
4. 补充缺失竖线：收集每个 lane 的活动行（含 `\` `/` 隐式引入的 lane），相邻活动行之间无 vline 则补
5. 颜色分配：lane → 分支名 → hash → 10 色调色板

#### 输出结构

```go
GraphOutput{
    MaxLane:  int        // SVG 宽度计算
    Rows:     int        // 总行数（含连接线行）→ SVG 高度
    Nodes:    []NodeData // {row, lane, sha, message, author, date, color}
    Segments: []SegData  // {from_lane, to_lane, row, type, color}
}
```

#### 前端简化

[`GitGraphCanvas.tsx`](../launcher/frontend/src/components/GitGraphCanvas.tsx)：~80 行，零 `useMemo`，零解析逻辑。

```tsx
// segments → <line>
segments.map(s => <line x1={x(s.from)} y1={y(s.row-1)} x2={x(s.to)} y2={y(s.row)} stroke={s.color} />)
// nodes → <circle> + <text>
nodes.map(n => <circle cx={x(n.lane)} cy={y(n.row)} fill={n.color} />)
```

#### 踩过的坑

| 问题 | 根因 | 修复 |
|------|------|------|
| 纯线性历史无竖线 | git 在单 lane 时不输出 `\|` | 收集活动行，相邻行补 vline |
| merge 后竖线断裂 | `\|/` 下一行 `*` 无 `\|` | 同上 |
| 分支内部竖线缺失 | `\` 引入的 lane 无显式 `\|` | 活动行收集纳入 `\` `/` 的 fromLane/toLane |
| fork 点"无源"竖线 | fork 斜线终点到第一个 commit 需竖线连接 | 预期行为，fork 点是线交点不是圆点 |

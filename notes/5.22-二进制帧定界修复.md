# 二进制长度前缀帧：修复流式响应分包导致工具调用死循环

## 现象

多工具调用场景下，后端反复处理同一个 `tool_call_id`，前端的 `ToolRequestPanel` 永不更新为下一个待审批工具，形成死循环。

### 日志证据

```
[ToolRequestPanel] 待审批工具（后端计算）:
  tool_call_id: call_01_8m1x66n0tDnBhk8Ymvyo2238
  tool_name: read
  arguments: {"filePath": "F:/1/ai-novelist/data/config/store.yaml"}
                         ← ToolRequestPanel 日志只打印了一次，从未改变
                         ← 控制台出现 4 次"无法解析chunk"
```

后端日志显示 `call_01` 被反复处理，`call_02` ~ `call_14` 从未被执行。

### 数据库证据

`call_01` 的 tool 消息被重复存储了 5 次，`active_leaf` 始终指向最后一次重复结果。`call_02` 的工具结果从未出现。

## 诊断推理链

### 第 1 步：发现反常重复处理模式

后端日志中 `call_01`（read store.yaml）被处理了 5 次，但 `call_02`（read skills.yaml）从未被存储。

```
21:44:32  → 处理 call_02 (skills.yaml)  → MCP 初始化...
21:44:32  → 又处理 call_01 (store.yaml)  → MCP 初始化...  ← 异常！
21:44:33  → 又 logging call_02...
21:44:44  → 又处理 call_01...
21:45:25  → 又处理 call_01...
...循环...
```

**推论：后端不知道 `call_01` 已经被处理过，说明 `state_update` 没有正确到达前端。**

### 第 2 步：反向推断

`_get_pending_tool_calls()` 遍历活跃路径，找最后一个 assistant 消息的 tool_calls，过滤已有 tool 消息。

如果后端每次都知道 `call_01` 待审批，说明它认为 `call_01` 的 tool 消息不在活跃路径上。

但数据库显示 `call_01` 的 tool 消息被存了 5 次，每次 `active_leaf` 都已更新。

**矛盾：数据库有，但 `_get_pending_tool_calls` 看不到 → 只能是前端没收到 `state_update`。**

### 第 3 步：验证前端视角

前端解析逻辑（修改前）：

```typescript
const chunk = decoder.decode(value, { stream: true });
const lines = chunk.split('\n').filter(line => line.trim() !== '');
for (const line of lines) {
    const parsed = JSON.parse(line);  // ← 唯一会报错的位置
}
```

4 次 parse 失败 = 4 个 `reader.read()` 拿到的数据不能拼成合法 JSON。`state_update` 的 JSON 本身是合法单行（`json.dumps` 转义了内部换行符），连续 4 次都失败——**唯一解释：JSON 行被 TCP 分包截断了。**

### 第 4 步：定量估算

那次 `glob` 结果有 70+ 行文件路径，`store.yaml` 有 294 行内容，加上前面所有工具结果...

**整个 `state_update` 的 JSON 体积估算在 50KB+。**

HTTP/1.1 `Transfer-Encoding: chunked` 下典型 TCP 包大小 ~8KB 到 ~64KB。50KB 的 JSON 必然被拆成多个 TCP segment。

`ReadableStreamDefaultReader.read()` 每次返回的字节数**不保证是一条完整消息**——它返回底层流缓冲区当前可读的数据量。

```
reader.read() #1 → 拿到 state_update 的前 30KB（不完整 JSON）
reader.read() #2 → 拿到剩下的 20KB（函数不再 yield，仅有这些）
```

第一次 parse 失败（碎片），第二次也失败... `nextPendingTool` 永不更新 → 死循环。

### 第 5 步：排除其他原因

- ❌ **不是 MCP 问题**：MCP 每次工具调用重新初始化是设计如此
- ❌ **不是后端逻辑错误**：`_get_pending_tool_calls` 逻辑正确，只是前端没收到更新
- ❌ **不是前端 dispatch 问题**：`setMessagesTree` 根本没被调用到（parse 就失败了）
- ❌ **不是并发竞争**：所有工具串行处理（HTTP 请求-响应模型）

**✅ 唯一覆盖所有现象的结论：TCP 分包导致 JSON 碎片。**

## 解决方案：二进制长度前缀帧

### 协议格式

```
┌─────────────┬──────────────────────────────┐
│  4 字节      │       N 字节                  │
│  长度 N      │      JSON payload            │
│  (uint32)   │  (UTF-8 编码)                │
│  大端序      │                              │
└─────────────┴──────────────────────────────┘
```

### 修改的文件

| 文件 | 改动 |
|------|------|
| [`backend/api/chat_api2.py`](../../backend/api/chat_api2.py) | 新增 `_encode_message()`；所有 `yield json_str + "\n"` 改为 `yield _encode_message(data)`；`StreamingResponse` media_type 改为 `application/octet-stream` |
| [`frontend/src/utils/binaryFrameReader.ts`](../../frontend/src/utils/binaryFrameReader.ts) | **新建** — `BinaryFrameReader` 类（字节级帧定界）+ `readBinaryFrames` 工具函数 |
| [`frontend/src/components/chat/ToolRequestPanel.tsx`](../../frontend/src/components/chat/ToolRequestPanel.tsx) | `handleFunctionCalling` 中流式解析从 `split('\n')` + `try/catch` 改为 `readBinaryFrames` 回调 |
| [`frontend/src/components/chat/MessageInputPanel.tsx`](../../frontend/src/components/chat/MessageInputPanel.tsx) | `sendMessage` generator 改用 `BinaryFrameReader` 产出已解析对象；消费端移除 `split('\n')` + `try/catch` |
| [`frontend/src/components/chat/MessageDisplayPanel.tsx`](../../frontend/src/components/chat/MessageDisplayPanel.tsx) | `regenerateMessage` 和 `confirmEdit` 两处均改用 `readBinaryFrames`；移除旧的 `processStateUpdateLine` |

### 为什么二进制长度前缀能解决

- **字节计数**，不依赖任何特殊字符做分隔
- JSON 内容里无论有什么（换行符、引号、Unicode），长度前缀不会歧义
- **TCP 分包完全免疫**：状态机按精确字节数读取，包被切成 100 片也能正确还原
- 前端只用 `Uint8Array.slice()` 切分，无多次 JSON 解析
- 可扩展：可在头 4 字节里加标志位（type、compress flag）

### 关键代码

```python
# 后端编码
def _encode_message(data: dict) -> bytes:
    json_bytes = json.dumps(data, ensure_ascii=False).encode('utf-8')
    return pack('>I', len(json_bytes)) + json_bytes
```

```typescript
// 前端读取
const frameReader = new BinaryFrameReader();

// reader.read() 循环中
frameReader.append(value);
let msg;
while ((msg = frameReader.readMessage()) !== null) {
    // msg 是完整的已解析 JSON 对象
    handleMessage(msg);
}
```

## 注意事项

1. 重启后端后生效，前端 HMR 自动生效
2. 旧的 NDJSON 格式不再兼容，升级后需重启前后端
3. `chat_api.py`（v1）不使用流式响应，无需修改
